1. Visión General

Este pipeline combina dos sistemas complementarios para producir papers académicos de alto impacto de forma casi completamente automatizada:

Papers-HQ (Stages 1–3.7)

Se encarga de la fase exploratoria: descubrir datos y literatura, generar ideas de investigación, validarlas rigurosamente, y generar un checklist de requisitos pre-código. Está compuesto por tres repositorios independientes:

  • search-repositories/ — Discovery (Path A)
  • analyze-data/ — Discovery (Path B)
  • research-junshi/ — Ideation
  • idea-evaluation-pipeline/ — Validation

Clo-Author (Stages 4–7)

Se encarga de la fase de ejecución: formalizar la estrategia, correr el análisis econométrico, escribir el paper, someterlo a peer review simulado, y preparar el paquete de envío. Stages 4 y 5 usan intervención manual (Claude en conversación), no agentes automatizados.

Checkpoints e Intervenciones Manuales

El pipeline tiene dos checkpoints humanos en las decisiones más críticas de un paper empírico:
Stage 2.5 — Idea Selection: el usuario elige qué idea investigar del top 3 generado automáticamente.
Stage 3.5 — Strategy Review: el usuario aprueba la estrategia de identificación causal antes de la ejecución.
Además, Stages 4 y 5 usan intervención manual de Claude (en conversación con el usuario), no subprocesos automatizados.

Principios de diseño

  • Automatización donde conviene: Stages 1, 2, 3, 3.7, 4.5, 6, 7 son automáticos — buscar repos, generar ideas, validar, auditar datos y revisar no requiere intervención.
  • Control humano donde importa: Stage 2.5 (qué investigar) y Stage 3.5 (cómo identificarlo) — las dos decisiones más importantes de un paper empírico.
  • Intervención manual (Claude en conversación): Stages 4 y 5 — la generación de código y escritura del paper se realizan manualmente con Claude en conversación, no mediante agentes automatizados.
  • Quality gates en cada fase: Umbrales determinísticos para avanzar entre stages.
  • Python exclusivo: Todo el análisis econométrico/estadístico usa Python.
  • Sin redundancias: Stage 3 evalúa el diseño de investigación, Stage 6 evalúa el paper completo.

Flujo completo

--topic "Economics" [+ --data] o --path-c → Stage 1 (Discovery: Path A, B, o C) → dataset + profile →
Stage 2 (Ideation) → Top 3 ideas → Stage 2.5 (Usuario elige) →
Stage 3 (Validation, score ≥ 7) → PROMPT.md → Stage 3.3 (Quick Test en datos reales) →
Stage 3.5 (Usuario aprueba) → Stage 3.7 (Referee Preview + assumption audit) → referee_checklist.md →
Stage 4 (Strategy + Code, intervención manual Claude) → results_summary.md →
Stage 4.5 (Data Audit automático) → data_audit.md →
Stage 5 (Writing, intervención manual Claude) → main.tex → Stage 6 (Peer Review, umbrales determinísticos) →
Accepted paper → Stage 7 (Submission, score ≥ 85) → Paper PDF final + feedback.pdf

2. Stage 1: Discovery

Objetivo: Obtener una base de datos y 3 papers académicos relacionados que sirvan como semilla para la generación de ideas. El usuario elige uno de dos caminos:

Path A: Búsqueda de repositorios — search-repositories/

Se activa cuando el usuario proporciona solo --topic.

#PasoDetalle
1Búsqueda en GitHubReplication packages de papers publicados con mínimo 50 estrellas o 20 forks.
2Agrupación temáticaLos repositorios se agrupan por área temática amplia y se ranquean por star score.
3Selección de áreaEl usuario selecciona un área temática de las disponibles.
4Búsqueda web de papers3 papers académicos publicados del área seleccionada (Scholar, SSRN, arXiv).

Output A: Repos de GitHub (URL, paper, DOI, dataset) + 3 seed papers.

Path B: Datos del usuario — analyze-data/

Se activa cuando el usuario proporciona --data <URL|archivo>.

#PasoDetalle
1Carga e inspecciónVariables, tipos, N observaciones, cobertura temporal/geográfica, estructura (cross-section, panel, serie de tiempo).
2Early warningSi el dataset parece inadecuado (pocas obs., pocas variables, sin variación), se muestra: "⚠ Este dataset tiene N=47 obs. y 3 variables — ¿estás seguro?". El usuario confirma o cambia de dataset.
3Perfil de datosEstadísticas descriptivas, patrones de missingness, variables potenciales de tratamiento/outcome.
4Búsqueda de papers3 papers relacionados con: (a) el área temática del --topic, (b) el contexto de los datos, y (c) metodologías aplicables a la estructura de datos detectada.

Output B: Perfil del dataset (variables, estructura, summary stats) + 3 seed papers.

Ejemplo: Si el usuario sube un panel de empleo en México 2010-2020 con --topic "Labor Economics", los 3 papers buscados serán sobre economía laboral en LATAM, con metodologías aplicables a datos de panel (DiD, event studies, etc.).

Path C: Data-First — --path-c (RECOMENDADO para scores 90+)

Se activa con --path-c. Busca los mejores datasets disponibles mundialmente y sugiere topics basados en lo que la data puede soportar.

#PasoDetalle
1Búsqueda curadaLista priorizada: RCTs primero, luego natural experiments, luego observacional. 12+ paquetes de replicación de top journals (QJE, REStat, etc.).
2Búsqueda en APIsHarvard Dataverse + Zenodo con queries de: "RCT replication", "natural experiment", "staggered rollout", "regression discontinuity".
3Descarga y perfilDescarga automática, perfila estructura, evalúa score ceiling. Solo datasets con ceiling ≥ 85 califican. RCTs reciben boost automático a ceiling 90+.
4Sugerencia de topicsClaude sugiere 2 topics por dataset. Cada sugerencia incluye: identification_level (A/B/C), control_group, y score_potential. Nunca sugiere Level C.
5Selección del usuarioEl usuario elige topic + dataset. El pipeline continúa con Path B (data ya descargada).

Output C: Dataset descargado + topic con identificación Level A/B + perfil completo.

Priorización: Tier 1 (RCT/experiment, ceiling 90+) > Tier 2 (natural experiment/staggered DiD, ceiling 85+) > Tier 3 (observational panel, ceiling 75+). Los datasets se prueban en orden de prioridad — RCTs primero.

Handoff a Stage 2 (todos los paths)

→ 3 seed papers (título, autores, DOI, resumen) + contexto del dataset → research-junshi

Modo: Completamente automático. No requiere intervención del usuario.

3. Stage 2: Ideation — research-junshi/

Objetivo: Generar y rankear ideas de investigación novedosas basándose en los seed papers de Stage 1.

Input

3 seed papers de Stage 1 (títulos, DOIs, resúmenes) + configuración de área de investigación y venues objetivo.

Proceso

#PasoDetalle
1Lectura de seed papersAnálisis profundo de los 3 papers semilla identificados en Stage 1.
2Búsqueda en arXivPapers publicados en las últimas 24 horas relacionados con los temas de los seeds.
3Búsqueda en target venuesExploración de journals específicos del campo para identificar tendencias actuales.
4Generación de ideasSe generan entre 8 y 10 ideas de investigación originales.

Output

Archivos: stage2_ideation.md, pipeline_state.json (actualizado)
Contenido:

  • Conexiones con la literatura existente
  • Top 3 ideas rankeadas con justificación
  • Ranked ideas JSON para handoff a Stage 2.5

Handoff a Stage 2.5

→ Top 3 ideas rankeadas con scores, justificaciones y datos requeridos → presentadas al usuario

3b. Stage 2.5: Idea Selection — Human-in-the-Loop

Objetivo: Permitir que el usuario elija qué idea de investigación desarrollar, basándose en el ranking generado automáticamente por Stage 2.

¿Qué se presenta al usuario?

Las 3 mejores ideas de Stage 2, cada una con:

ElementoDetalle
Research questionFormulación precisa de la pregunta de investigación
Metodología propuestaEstrategia de identificación causal sugerida (DiD, RDD, IV, etc.)
Score compuestoN × 0.2 + F × 0.2 + I × 0.2 + ID × 0.4 (Identification-first)
Justificación del rankingPor qué esta idea rankea donde rankea vs. las otras
Datos requeridosDatasets específicos necesarios y su disponibilidad
Conexión con literaturaPapers más cercanos y cómo se diferencia la idea

Decisión del usuario

DecisiónAcciónResultado
✓ SELECCIONARElegir una de las 3 ideasLa idea seleccionada se formatea como idea_template.txt y pasa a Stage 3
⊕ COMBINARFusionar elementos de 2+ ideasSe crea una idea híbrida con elementos de múltiples propuestas → Stage 3
✗ RECHAZAR TODASNinguna idea es satisfactoriaSe regresa a Stage 2 con feedback del usuario para generar nuevas ideas
¿Por qué es crítico este paso? El ranking automático (N×0.4 + F×0.3 + I×0.3) no puede capturar el conocimiento de dominio del investigador, su familiaridad con los datos, o su agenda estratégica de publicación. Un investigador puede preferir la idea #3 porque tiene acceso privilegiado a los datos, o la #2 porque se alinea con su programa de investigación.

Output

selected_idea.md — La idea seleccionada (o combinada) por el usuario, formateada como idea_template.txt: título, pregunta de investigación, estrategia de identificación, fuentes de datos, y los 3 papers más cercanos.

Handoff a Stage 3

→ selected_idea.md formateada como idea_template.txt para el pipeline de evaluación

4. Stage 3: Validation — idea-evaluation-pipeline/

Input: selected_idea.md del Stage 2.5 (idea elegida por el usuario)

Objetivo: Evaluar rigurosamente la idea de investigación mediante un pipeline de 8 pasos iterativo hasta alcanzar un score ≥ 7/10.

Input

Un archivo idea_template.txt con: título, pregunta de investigación, estrategia de identificación, fuentes de datos, y los 3 papers más cercanos (con cita completa).

Proceso — Pipeline de 8 pasos con loop

#PasoDescripciónModelo
1Literature CheckVerificar novedad contra la literatura existenteSonnet
2Idea RefinementAfilar la pregunta de investigación y el alcanceSonnet
3Methodology ReviewEvaluar la validez de la estrategia de identificaciónSonnet
4Data FeasibilityConfirmar disponibilidad y adecuación de los datosSonnet
5Pre-Analysis PlanFijar especificaciones antes del análisisSonnet
6Draft EvaluationEvaluar completitud del diseño de investigaciónOpus
7Design Peer SimRevisión simulada del diseño (no del paper completo)Opus
8Final ScoreAsignación del score final 1-10Opus
Loop: Si el score < 7, se regresa al paso 2 con feedback. Máximo 5 iteraciones. Si tras 5 loops el score sigue < 7, el pipeline se detiene con aviso: "⚠ Idea estancada tras 5 rondas de refinamiento (mejor score: X/10). Regresando a Stage 2.5 para seleccionar otra idea." Solo si las 3 ideas fueron agotadas se vuelve a Stage 2.
Nota sobre el paso 7: La simulación de peer review en Stage 3 evalúa únicamente el diseño de investigación (pregunta, método, datos, viabilidad). No evalúa un paper completo — eso lo hace Stage 6 con el manuscrito terminado. Esto evita redundancia.

Output

Archivos: stage3_validation.md, evaluation/idea.txt, PROMPT.md
Contenido: Idea aprobada (score ≥ 7), pregunta refinada, metodología refinada, pre-analysis plan (PAP), reportes de evaluación de cada paso.

Handoff a Stage 3.5

→ PROMPT.md + reportes de evaluación presentados al usuario para revisión de estrategia

Modo: Completamente automático (el loop interno es automático; la intervención humana ocurre en Stage 3.5).

4b. Stage 3.3: Quick Empirical Test

Objetivo: Verificar que la estrategia de identificación propuesta funciona en los datos reales ANTES de invertir tiempo en generación de código y escritura del paper.

Input

Dataset del usuario + idea seleccionada de Stage 2.5.

Proceso — 5 tests automáticos

#TestQué verificaSi falla
0Estimator availabilityTesta pyfixest, linearmodels, csdid en los datos reales. Registra cuáles funcionan y cuáles no.Marca estimador como BROKEN — Stage 4 no lo usará
1Basic DiDRegresión rápida: outcome ~ treat + entity_FE + time_FE, clustered SEsPuede indicar efecto nulo o datos inadecuados
2Permutation test200 reshuffles del tratamiento. ¿El efecto real está en la cola?Si p > 0.1, la identificación es frágil
3Entity trends¿El efecto sobrevive tendencias lineales por entidad?Si desaparece, es pre-tendencia, no tratamiento

Decisión del usuario

ResultadoAcción
PASSTodos los tests pasan → proceder con confianza
WARNAlgunos tests pasan con flags → proceder con precaución (-5 score)
FAILPermutation o trends eliminan el efecto → usuario elige: (1) Proceder con ceiling ~70, (2) Elegir otra idea (→ Stage 2.5), (3) Proveer nuevos datos
¿Por qué es crítico? En el proyecto oil-democracy, Stage 3.3 hubiera detectado que el permutation p = 0.588 y country trends eliminaban el efecto ANTES de generar 4 scripts y un paper de 31 páginas, ahorrando horas de trabajo.

Output

pipeline_state.json actualizado con:
available_estimators: qué paquetes funcionan en estos datos
estimator_warnings: qué falló y por qué
quick_test_results: ATT, permutation p, trends p

Handoff a Stage 3.5

→ Estimadores verificados + test results → presentados al usuario junto con la estrategia

Modo: Completamente automático (~30 segundos).

5. Stage 3.5: Strategy Review — Human-in-the-Loop (2do checkpoint)

Objetivo: Asegurar que el usuario valide la estrategia de identificación causal antes de comprometer recursos en la ejecución.

¿Qué se presenta al usuario?

  • Pregunta de investigación — formulación exacta
  • Método causal propuesto — DiD, RDD, IV, matching, etc.
  • Fuentes de datos — datasets específicos con detalles de acceso
  • Variables clave — tratamiento, outcome, controles
  • Supuestos clave — parallel trends, exclusion restriction, etc.
  • Amenazas a la validez — confounders, selection bias, measurement error
  • Resumen del Pre-Analysis Plan

Decisión del usuario

DecisiónAcciónResultado
✓ APPROVEProceder a Stage 3.7Se genera approved_strategy.md como contrato vinculante
↺ REFORMULATEAjustar estrategia según feedbackSe re-presenta la estrategia modificada al usuario
✗ REJECTRegresar a Stage 2.5El usuario elige otra idea del top 3. Si las 3 fueron agotadas, se vuelve a Stage 2
¿Por qué es crítico este paso? La estrategia de identificación es la decisión más importante de un paper empírico. Un paper técnicamente perfecto con una estrategia débil será rechazado por los referees. Este checkpoint cuesta poco tiempo y previene el error más costoso del pipeline.

Output

approved_strategy.md — La estrategia de identificación validada por el usuario. Este documento se convierte en el contrato vinculante para todas las etapas siguientes.

Handoff a Stage 3.7

→ approved_strategy.md — estrategia validada por el usuario, lista para referee preview

5b. Stage 3.7: Referee Preview

Objetivo: Simular 2 referees antes del código para generar un checklist de requisitos que el análisis y el paper deberán cumplir.

Input

approved_strategy.md de Stage 3.5 — la estrategia de identificación validada por el usuario.

Proceso — Dos referees simulados + assumption audit

Domain Referee

Evalúa desde la perspectiva del campo:

  • Contribución a la literatura
  • Gaps en la literatura que se deben cubrir
  • Construcción y fuentes de datos
  • Tablas y figuras necesarias para convencer

Methods Referee

Evalúa la solidez metodológica:

  • Estrategia de inferencia causal
  • Tests de especificación requeridos
  • Checks de robustez necesarios
  • Pitfalls y errores comunes a evitar
Assumption Audit por método (NUEVO): Checklists específicos según el diseño causal:
DiD: parallel trends, no-anticipation, composición estable, HonestDiD sensitivity
IV: first-stage F > 10, exclusión restriction, monotonicity, Anderson-Rubin CIs
RDD: McCrary density test, bandwidth sensitivity, donut-hole, continuidad de covariables
RCT: balance table + joint F-test, permutation inference, attrition, Lee bounds, Cohen's d
SC: pre-treatment RMSPE, predictor balance, donor pool justification, permutation inference
Filtro de estimadores: El checklist se cruza contra los estimadores verificados en Stage 3.3. Si un estimador está marcado como BROKEN, los requisitos que lo necesitan se marcan como [DOWNGRADED] y no se prometen en Stage 4.

Output

strategy/referee_checklist.md — Checklist estructurado con las siguientes categorías:
  • MUST-HAVE: Requisitos indispensables que el paper debe cumplir
  • SHOULD-HAVE: Elementos altamente recomendados
  • NICE-TO-HAVE: Elementos opcionales que fortalecen el paper
  • WARNINGS: Riesgos y amenazas identificadas por los referees
  • MUST-NOT-CLAIM: Claims que el paper no debería hacer dado el diseño
Diferencia con Stage 3 y Stage 6: Stage 3 evalúa si la idea es viable; Stage 3.7 genera un checklist de requisitos para guiar la implementación; Stage 6 evalúa el paper completo. No hay redundancia: cada stage opera sobre un artefacto distinto en un momento distinto del pipeline.

Handoff a Stage 4

→ referee_checklist.md — checklist de requisitos que guía la generación de código y escritura en Stages 4-5

Modo: Completamente automático.

6b. Stage 4.5: Data Audit

Objetivo: Sanity checks automáticos sobre clean_data ANTES de escribir el paper. Detectar problemas en los datos que podrían invalidar los resultados.

Input

clean_data.csv producido por Stage 4 + results_summary.md.

Proceso — 4 checks automáticos

#CheckDetalleCriterio de flag
1Distribution checksDistribución de variables clave vs. rangos esperadosVariables fuera de rangos plausibles → flag de posible error de codificación
2Cell sizesTamaños de celda por grupo de interacción (tratamiento × subgrupo)N < 30 en alguna celda → flag de poder estadístico insuficiente
3Outcome distributionDistribución del outcome: zero rate, skewness, outliers extremosZero rate alto, skewness extrema, o outliers > 3 SD de la media
4Outlier detectionObservaciones con valores extremos que distorsionan la estimaciónValores > 3 SD, ratio max/min extremo, o distribución muy sesgada

Output

data_audit.md — Reporte completo de los 4 checks con:
  • Resultado de cada check (PASS / WARNING / CRITICAL)
  • Estadísticas descriptivas de soporte
  • Recomendaciones de acción para cada flag
Flags CRITICAL: Si algún check produce un flag CRITICAL, el pipeline advierte al usuario antes de proceder a Stage 5. El usuario decide si continuar, ajustar los datos, o regresar a Stage 4 para re-limpiar.
Uso posterior: data_audit.md se incluye en el evidence packet que reciben los referees en Stage 6, proporcionando evidencia de que los datos fueron auditados antes de la escritura del paper.

Handoff a Stage 5

→ data_audit.md — reporte de auditoría de datos, listo para ser referenciado en el paper

Modo: Completamente automático.

Compilación automática

Pipeline de compilación: pdflatex × 3 pasadas + bibtex → PDF. Si la compilación LaTeX falla, se usa fallback con fpdf2 para generar un PDF funcional.

Estándares de formato

Documento

  • LaTeX, \documentclass[12pt]{article}
  • Márgenes: 1 pulgada (geometry)
  • Cuerpo: \doublespacing
  • Bibliografía: biblatex + biber

Tablas y figuras

  • Tablas: booktabs (toprule, midrule, bottomrule)
  • Notas obligatorias en toda tabla y figura
  • Captions: font-small, bold labels

8. Stage 6: Peer Review — Clo-Author

Objetivo: Simular un proceso de revisión por pares realista, con un editor y dos referees independientes, usando umbrales determinísticos para la decisión editorial.

Input

paper/main.tex compilado como PDF.

Sub-fase 6a: Desk Review (editor)

Evaluación inicial: verificación de novedad (web search), evaluación de journal fit, decisión de enviar a referees o desk reject.

Si el editor hace desk reject, el paper regresa a Stage 5 con feedback específico.

Sub-fase 6b: Referee Reports (ciegos, independientes, en paralelo)

Domain-referee

Evalúa desde la perspectiva del campo: contribución a la literatura, cobertura, validez externa, relevancia para el journal.

Methods-referee

Evalúa la solidez metodológica: identificación causal, inferencia estadística, robustez de resultados, calidad del análisis.

Evidence packet (los referees reciben)

Además del PDF del paper, los referees reciben: data_audit.md, results_summary.md, cell_sizes.csv, tablas .tex reales del código, y un code review. Field calibration: prácticas estándar de CHE (health economics) no se penalizan; los referees deben verificar claims contra la evidencia proporcionada.

Sub-fase 6c: Decisión editorial — Umbrales determinísticos

El editor clasifica cada concern (FATAL / ADDRESSABLE / TASTE) y aplica umbrales determinísticos:

CondiciónDecisión
avg_score ≥ 75 AND no fatalACCEPT
avg_score ≥ 75 AND fatalMINOR REVISIONS
avg_score 60-74 AND no fatalMINOR REVISIONS
avg_score 60-74 AND fatalMAJOR REVISIONS
avg_score 40-59MAJOR REVISIONS
avg_score < 40 AND fatalREJECT
R&R loop: Máximo 3 rondas. En ronda 2+, referees verifican si concerns anteriores fueron addressed. Tras agotar las rondas de R&R, el usuario siempre recibe 3 opciones:
[1] Aceptar score actual → Stage 7
[2] Manual fix → re-review
[3] Restart desde Stage 3.7 (reconstruir código + paper)

Output

quality_reports/reviews/ — Reportes de referees + decisión editorial
response_letter.md — Carta de respuesta punto por punto (si hay R&R)
